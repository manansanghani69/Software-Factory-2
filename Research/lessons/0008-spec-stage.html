The Spec Stage: Thinking Before Acting

Upstream of Sandcastle — where your pipeline decides what and in what order before it runs.

Recall before reading

From lesson 0007: what does the plan step emit, and what does the orchestrator do with it? Now consider — if two issues both edit lib/factory.ts, what happens if they run in parallel?

Why this matters

Sandcastle is a flawless pair of hands and a terrible brain. It will fan out every open issue in parallel — including issues that depend on each other — and then let you discover the merge conflicts. If your factory is to run fully autonomous, the thinking must happen before execution: write a spec per issue, name its dependencies, and let Sandcastle only do what it's good at.

The honest constraint

Sandcastle has zero awareness of issue dependencies. It doesn't read the repo's graph, it doesn't know that fixing a parser must land before a formatter. Parallelism safety is decided by you (or your planner agent): two issues may run concurrently only if they touch no shared files and have no transitive dependency on each other.

Everything good about running agents — the branch strategy reusing and fast-forwarding worktrees, Promise.all, structured output — is machinery. The dependency map is meaning. Sandcastle gives you all the machinery; the planner supplies the meaning.

The spec stage in three jobs

  1. Specify — a planner agent reads the open issues and emits, for each, a checkable spec: scope, files touched, acceptance criteria, dependencies. One-shot run + Output.object() (lesson 0006), so the spec's shape is schema-validated before anything else happens.
  2. Schedule — your code turns the spec into waves: topological layers. Wave members must be mutually independent. The machine does the ordering — not the LLM — because it's deterministic and testable.
  3. Execute — each wave runs the parallel implement → gate → review loop from lesson 0007, then merges. The next wave's branches start from the newly merged HEAD, so dependents see their dependencies' work.
The divider of labor

LLMs reason about intent: "this issue rewrites the auth module, and that one depends on the new token shape." Machines reason about order: "run wave 1, wait, run wave 2." Split the work there. If the planner emits an ordering and lets it become a lie (stale branch, missed dependency), the machine can't catch it — so make the planner emit evidence (files, dependencies), and let your code compute the waves from that evidence.

The plan prompt — emit evidence, not orders

# .sandcastle/plan.md — the spec stage (single-iteration, structured output)
Analyze the open issues and produce a dependency-aware spec.

#\`gh issue list --state open --json number,title,body,labels --limit 30\`

#\`git log --oneline -10\`

Emit JSON inside <plan> tags, shape:

{ "issues": [
  { "number": string,
    "scope": string,
    "files": [string],
    "dependencies": [string],
    "acceptance": [string]
  } ] }

- files: every file the fix will touch, best effort.
- dependencies: issue numbers that must land before this one.
- parallelizable — do NOT include it; the orchestrator computes waves
  from files and dependencies. Your job is evidence, not scheduling.
When done, print <promise>COMPLETE</promise>.

The scheduler — waves in your code

Your orchestration turns the validated spec into execution waves:

const wavesOf = (issues) => {
  const completed = new Set();
  const waves = [];
  let pending = issues.map(i => i.number);

  while (pending.length) {
    const ready = issues.filter(i =>
      pending.includes(i.number) &&
      (i.dependencies ?? []).every(d => completed.has(d))
    );
    if (!ready.length) throw new Error("Circular dependency in plan");
    ready.forEach(i => completed.add(i.number));
    pending = pending.filter(n => !ready.some(i => i.number === n));
    waves.push(ready);
  }
  return waves;
};

Then the execution loop — wave by wave, merge between waves so dependents fast-forward onto fresh work:

// plan.output.issues is validated; scheduler is deterministic
for (const wave of wavesOf(plan.output.issues)) {
  await Promise.all(wave.map(fixAndReview)); // lesson 0007's loop
  for (const issue of wave) {
    execSync(`git merge agent/fix-${issue.number} --no-edit`, { stdio: "inherit" });
  }
  console.log(`wave complete: ${wave.map(i => i.number).join(", ")}`);
}
This is the dependency answer

Yes — Sandcastle picks up independent tickets in parallel, across waves of dependent ones. Independent issues share a wave; dependent issues wait for their wave's merge, then their branch starts from the new HEAD and fast-forwards over the dependency's changes. The branch strategy's re-run reuse (ADR 0003) is what makes the fast-forward cheap.

The factory is complete

You now have the full architecture: spec stage (this lesson) → parallel implement → gate → review → wave merge (lessons 0001–0007). The only humans left are the ones writing the issues — and nothing in this stack stops you from giving that job to a triage agent too. That's the whole shape of a software factory.

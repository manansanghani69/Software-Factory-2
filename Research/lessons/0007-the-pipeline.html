The Capstone: Your Autonomous Pipeline

Plan → implement → gate → review → merge. No human in the loop.

Recall before reading

Without looking, name the six mechanics this course has taught you, in the order you'd need them to build a pipeline that fixes GitHub issues and merges the results.

The mission, assembled

Everything you've learned feeds one loop. A planner looks at your open issues and emits a validated plan; parallel fix agents work each issue on its own branch; a test gate stops broken work; a reviewer tidies each branch; and green branches merge back. That's the factory — this lesson wires every wire together.

The shape of the pipeline

  1. Plan — one-shot run() + Output.object(). The planner reads open issues via !`gh issue list…` and emits a validated JSON plan (which issues are parallelizable, in what order). Lesson 0006.
  2. Fan out — Promise.all over the plan's issues, each in its own createSandbox() on its own named branch. Lessons 0005, 0002.
  3. Implement — sandbox.run() with a prompt file using {{ISSUE_NUMBER}} plus live context. Lessons 0004, 0001.
  4. Gate — sandbox.exec("npm test"); non-zero exit aborts that issue's review, preserving the branch for inspection. Lesson 0003.
  5. Review — a second sandbox.run() on the same warm container passes judgement and fixes stragglers. Lesson 0003.
  6. Merge — green branches merge back into HEAD. Learned this lesson.

The whole file

Three prompt files plus one main.ts. First, the prompts.

# .sandcastle/plan.md — the planner (structured output, single iteration)
Analyze the open issues in this repo.

#\`gh issue list --state open --json number,title,body,labels --limit 20\`

#\`git log --oneline -10\`

Emit your plan as JSON inside <plan> tags. Shape:

{ "issues": [ { "number": string, "summary": string, "parallelizable": boolean } ] }

Mark an issue parallelizable only if it touches no files another issue touches.
When done, print <promise>COMPLETE</promise>.
# .sandcastle/implement.md — the fix prompt
You are working on {{SOURCE_BRANCH}}. Compare against {{TARGET_BRANCH}}.

Fix GitHub issue #{{ISSUE_NUMBER}}.

#\`gh issue view {{ISSUE_NUMBER}} --json body,title -q '.body'\`

Follow the repo's conventions. Add or update tests. When the work is
committed and the build passes, print <promise>COMPLETE</promise>.
# .sandcastle/review.md — the reviewer (inline prompt equivalent shown next)
Review the changes on {{SOURCE_BRANCH}} against {{TARGET_BRANCH}}:
correctness, tests, conventions. Fix anything clearly wrong, then
print <promise>COMPLETE</promise>.

Now main.ts — the orchestrator:

import { run, createSandbox, Output, opencode } from "@ai-hero/sandcastle";
import { docker } from "@ai-hero/sandcastle/sandboxes/docker";
import { z } from "zod";
import { execSync } from "node:child_process";

// ---------- 1. PLAN (single-iteration, structured output) ----------
const plan = await run({
  agent: opencode("opencode/big-pickle"),
  sandbox: docker(),
  promptFile: ".sandcastle/plan.md",
  output: Output.object({
    tag: "plan",
    schema: z.object({
      issues: z.array(z.object({ number: z.string(), summary: z.string(), parallelizable: z.boolean() })),
    }),
  }),
});

// plan.output.issues is now typed and validated

// ---------- 2..5. IMPLEMENT → GATE → REVIEW, parallel per issue ----------
const fixAndReview = async (issue) => {
  await using sandbox = await createSandbox({
    branch: `agent/fix-${issue.number}`,
    sandbox: docker(),
    hooks: {
      sandbox: {
        onSandboxReady: [{ command: "npm install", timeoutMs: 300_000 }],
      },
    },
  });

  // implement
  await sandbox.run({
    agent: opencode("opencode/big-pickle"),
    promptFile: ".sandcastle/implement.md",
    promptArgs: { ISSUE_NUMBER: issue.number },
    maxIterations: 5,
  });

  // gate — non-zero exit aborts this issue's review
  const gate = await sandbox.exec("npm test");
  if (gate.exitCode !== 0) {
    throw new Error(`Tests failed on #${issue.number}:\n${gate.stdout}\n${gate.stderr}`);
  }

  // review (same warm container, same branch)
  await sandbox.run({
    agent: opencode("opencode/big-pickle"),
    promptFile: ".sandcastle/review.md",
    promptArgs: { ISSUE_NUMBER: issue.number },
    maxIterations: 3,
  });
};

const parallelizable = plan.output.issues.filter(i => i.parallelizable);

try {
  await Promise.all(parallelizable.map(fixAndReview));
} catch (err) {
  console.error("Pipeline stopped — investigate the failure:", err.message);
  process.exitCode = 1;
}

// ---------- 6. MERGE every green branch back ----------
for (const issue of parallelizable) {
  execSync(`git merge agent/fix-${issue.number} --no-edit`, { stdio: "inherit" });
}

console.log("All issues fixed, reviewed, and merged.");
What you own vs. what Sandcastle owns

Sandcastle's job ends when the reviewer's commits land on the branch. The merge back is your code (plain git in the harness here). On a remote repo, that merge becomes a push + gh pr merge --merge; either way, no human is required.

Fail loudly, preserve work

When one issue's tests fail, this pipeline throws and the surviving branches stay checked out — that's the await using cleanup preserving dirty worktrees so you can investigate. What's left of the loop keeps running: the try/catch catches the first failing issue while its siblings proceed.

Decide deliberately whether you want fail-fast (above: first failure stops the merge) or fail-open (below: review everything, merge only the green branches).

// Fail-open alternative: review everything, merge only the green.
const outcomes = await Promise.allSettled(parallelizable.map(fixAndReview));
const green = parallelizable.filter((_, i) => outcomes[i].status === "fulfilled");
for (const issue of green) {
  execSync(`git merge agent/fix-${issue.number} --no-edit`, { stdio: "inherit" });
}

Before you run it for real

  • Scratch repo first. Point the pipeline at a repo you own with a few open issues and a test suite. Never first-light this against production code.
  • Keep the plan single-iteration. Output.object() needs maxIterations: 1 (the default). The fix and review runs can loop.
  • opencode can't retry output. If the planner emits a malformed <plan>, the run fails — re-run it. For automatic retries you'd need a resumable provider (lesson 0006).
  • The template shortcut. npx @ai-hero/sandcastle init --template parallel-planner-with-review scaffolds all of this and more. This lesson is what's inside it, so you can bend it to your workflow rather than reverse-engineering the generated code.

Do it now

  1. Re-create the three prompts and main.ts above in your scratch repo. npm i -D zod first — the planner schema needs it.
  2. Run npx tsx .sandcastle/main.ts. If your repo has no open GitHub issues, hardcode the plan (define plan.output.issues directly) or use the custom tracker from init.
  3. Watch the log: the plan should be a validated JSON plan first, then parallel sandboxes for each issue.
  4. After it finishes: git log --oneline — you should see implement commits, review commits, and a merge commit, all with no human hands.
  5. Break one test deliberately, rerun, and confirm the gate blocks that issue's review while the others complete.

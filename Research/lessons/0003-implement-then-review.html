Lesson 0003

The Implement-then-Review Loop

Two agents, one branch, one container — gated by real test output.

Recall before reading

From lessons 0001–0002, answer without looking: what does branchStrategy: { type: "branch" } do, and why is it safer than head for repeated runs?

Why this matters

A single run() gives you an AFK agent. Two sequential run() calls give you an implementer and a reviewer — but each spins up and tears down its own container. createSandbox() gives you one warm container that survives across both, so the reviewer sees the exact state the implementer left behind, with dependencies already installed.

The lifecycle

createSandbox() creates a container + worktree pair. You own it until you close it — either explicitly or implicitly via await using:

await using sandbox = await createSandbox({
  branch: "agent/fix-42",
  sandbox: docker(),
  hooks: {
    sandbox: {
      onSandboxReady: [{ command: "npm install", timeoutMs: 300_000 }],
    },
  },
});

When the await using block exits — whether normally or via an exception — sandbox.close() fires automatically. If the worktree is dirty (uncommitted changes), it's preserved on disk; if clean, both container and worktree are removed. (README: cleanup)

Where hooks fire

Hooks are grouped by where they run — host or sandbox. The ordering is strict:

copyToWorktree
  → host.onWorktreeReady   // sequential, runs on your machine
  → [sandbox created]
  → host.onSandboxReady    // parallel with sandbox hooks, runs on your machine
  → sandbox.onSandboxReady // parallel with host hooks, runs INSIDE the container
HookRuns onWhen
host.onWorktreeReadyHostAfter worktree copy, before container starts. Use for host-side file prep (e.g. cp .env.example .env).
host.onSandboxReadyHostAfter container is up. Use for host-side verification you don't want inside the container.
sandbox.onSandboxReadySandboxAfter container is up. Use for dependency installs, database seeds — anything that needs to see the repo inside the container.

If any hook exits non-zero, setup fails fast. Host hooks accept { command, timeoutMs? }. Sandbox hooks also accept { command, sudo?, timeoutMs? } for elevated installs. (README: hooks)

Two hooks, both "ready"

host.onSandboxReady and sandbox.onSandboxReady fire at the same moment — one on the host, one inside the container. Use the sandbox variant when the command needs the container's repo state; use the host variant when it needs the host's file system.

The full pipeline

Three steps: implement → gate on tests → review. All in one sandbox, one branch, one await using block:

import { createSandbox, opencode } from "@ai-hero/sandcastle";
import { docker } from "@ai-hero/sandcastle/sandboxes/docker";

await using sandbox = await createSandbox({
  branch: "agent/fix-42",
  sandbox: docker(),
  hooks: {
    sandbox: {
      onSandboxReady: [{ command: "npm install", timeoutMs: 300_000 }],
    },
  },
});

// Step 1 — implement
const impl = await sandbox.run({
  agent: opencode("opencode/big-pickle"),
  promptFile: ".sandcastle/implement.md",
  maxIterations: 5,
});

// Step 2 — gate: run tests, abort review if they fail
const tests = await sandbox.exec("npm test");
if (tests.exitCode !== 0) {
  throw new Error(`Tests failed:\n${tests.stdout}\n${tests.stderr}`);
}

// Step 3 — review (same branch, same warm container)
const review = await sandbox.run({
  agent: opencode("opencode/big-pickle"),
  prompt: "Review the changes on this branch. Fix any issues you find.",
});

// Cleanup is automatic — await using calls sandbox.close()

Three things to notice:

  1. sandbox.exec() returns exitCode — it does not throw. You decide whether a non-zero exit is fatal. This makes it easy to gate on results without try/catch noise. (README)
  2. The container stays alive. npm install only runs once (in onSandboxReady). The review step sees the exact installed deps and build artifacts from the implement step.
  3. Commits accumulate on the same branch. Both sandbox.run() calls write to agent/fix-42. When the block exits, the branch has a clean history of implement + review commits.

Do it now

  1. Create .sandcastle/implement.md — write a prompt telling the agent to fix a small issue, and end with <promise>COMPLETE</promise>.
  2. Replace the run() call in main.ts with the full createSandbox() pipeline above.
  3. If your repo has tests, run it and watch the gate — the review should only start if npm test passes. If it doesn't, look at the thrown error and check .sandcastle/logs/.
  4. After the run, inspect: git log agent/fix-42 --oneline. You should see both implement and review commits on the same branch.
  5. Check git status — the worktree should be clean (auto-removed) or preserved if there were uncommitted changes.
Then what?

You now have the autonomous factory core: implement → gate → review. Next we make it dynamic: promptFile with !`command` expressions that pull live context (open issues, recent commits) into the prompt at runtime, and promptArgs for reuse across different issues. That turns a single hardcoded run into a real issue-driven pipeline.

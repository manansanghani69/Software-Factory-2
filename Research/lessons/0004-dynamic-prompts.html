Lesson 0004

Dynamic Prompts

Pull live context into your prompt at runtime — from the repo, from arguments, from both.

Recall before reading

From lessons 0001–0003: what does promptFile do that an inline prompt string does not, and why can't you use both at once?

Why this matters

Your implement-then-review pipeline from lesson 0003 works — but it's hardcoded to one issue. Dynamic prompts let you feed it any issue number and get live context (the issue body, recent commits, the branch name) injected automatically. That turns a demo into a real factory loop.

The three features

Everything below applies only to promptFile — inline prompt strings are passed to the agent literally, with no substitution, no expansion, no built-in injection. (README: prompt resolution)

1. promptArgs with {{KEY}}

Inject values into your prompt file at call time. Reuse the same prompt across different issues:

// main.ts — the call site
await sandbox.run({
  agent: opencode("opencode/big-pickle"),
  promptFile: ".sandcastle/implement.md",
  promptArgs: { ISSUE_NUMBER: "42", PRIORITY: "high" },
});
# .sandcastle/implement.md — the prompt
Work on issue #{{ISSUE_NUMBER}} (priority: {{PRIORITY}}).
When done, print <promise>COMPLETE</promise>.

A {{KEY}} placeholder with no matching prompt argument is an error. Extra prompt arguments you don't use produce a warning — safe, but noisy. (README)

2. Live context with !`command`

Shell expressions in your prompt file are replaced with the command's stdout — inside the sandbox, after sandbox.onSandboxReady hooks complete, so they see the repo state the agent sees:

# .sandcastle/implement.md
# Open issues

!\`gh issue list --state open --label Sandcastle --json number,title,body --limit 10\`

# Recent commits

!\`git log --oneline -10\`

Work on issue #{{ISSUE_NUMBER}}. Compare against {{TARGET_BRANCH}}.

All expressions run in parallel for faster expansion. If any command exits non-zero, the run fails immediately. (README)

3. Built-in prompt arguments

Sandcastle injects two automatically — no promptArgs entry needed:

PlaceholderValue
{{SOURCE_BRANCH}}The branch the agent works on
{{TARGET_BRANCH}}The host's active branch at run() time

You cannot override these via promptArgs — it's an error to try. (README)

Execution order

The three features fire in a strict sequence — this matters when {{KEY}} appears inside a !`command` expression:

  1. {{KEY}} substitution (on the host) — all placeholders, including those inside shell expressions, are replaced first.
  2. !`command` expansion (inside the sandbox) — the now-complete shell commands run and their stdout replaces the expression.
  3. Final prompt sent to the agent.

This means you can write:

!\`gh issue view {{ISSUE_NUMBER}} --json body -q .body\`

...and {{ISSUE_NUMBER}} is replaced before the shell command runs, so the correct issue is fetched. Safe and deliberate.

User content is safe inside promptArgs

A !`…` pattern that appears inside a prompt argument value is treated as inert text — it won't execute against the shell. You can pass issue titles, PR descriptions, or docs excerpts through promptArgs without risk. (README)

Put it together: an issue-driven pipeline

A single prompt file that works for any issue, with live context pulled from GitHub and git:

# .sandcastle/implement.md
You are working on {{SOURCE_BRANCH}}. Compare against {{TARGET_BRANCH}}.

#\`gh issue view {{ISSUE_NUMBER}} --json body,title -q '.body'\`

#\`git log --oneline -10\`

Fix the issue described above. When done, print <promise>COMPLETE</promise>.

The call site — any issue, any priority:

await sandbox.run({
  agent: opencode("opencode/big-pickle"),
  promptFile: ".sandcastle/implement.md",
  promptArgs: { ISSUE_NUMBER: "73", PRIORITY: "medium" },
});

Change the number, rerun. Same prompt, different issue, live context every time.

The completion signal lives in your prompt

Sandcastle never injects <promise>COMPLETE</promise> — it's a convention you document in the prompt for the agent to follow. You can override the default signal string by passing completionSignal to run(), or pass an array of alternatives:

await sandbox.run({
  agent: opencode("opencode/big-pickle"),
  promptFile: ".sandcastle/implement.md",
  completionSignal: ["TASK_COMPLETE", "TASK_ABORTED"],
});

Document whichever string(s) you choose in the prompt file, so the agent knows what to emit. The matched signal appears on result.completionSignal — useful for branching on whether work finished or was aborted.

Do it now

  1. Write .sandcastle/implement.md with !`git log --oneline -10` at the top and a {{ISSUE_NUMBER}} placeholder in the body.
  2. In main.ts, pass promptArgs: { ISSUE_NUMBER: "1" } to sandbox.run().
  3. Run it. Check .sandcastle/logs/ — you should see the expanded prompt with real git log output at the top.
  4. Change the issue number and rerun — same prompt, different context.
  5. Bonus: add a second !`gh issue view {{ISSUE_NUMBER}} --json body -q .body` expression and verify both run in parallel (check the log timestamps).
Then what?

You now have a reusable prompt that works for any issue. Next: parallel agents — running multiple implement-then-review loops on different issues simultaneously, each on its own named branch, in separate containers. That's the full factory.

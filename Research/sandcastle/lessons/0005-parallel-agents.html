Lesson 0005

Parallel Agents

The full factory — multiple issues, multiple agents, simultaneous branches.

Recall before reading

From lesson 0002: why is branchStrategy: { type: "branch" } the only safe choice when running two agents at once? What do head and merge-to-head do that makes them dangerous?

Why this matters

One agent is a demo. Three agents running on three issues simultaneously — each on its own branch, each in its own container, merging back when done — that's the autonomous factory you're building toward.

Two parallelism patterns

Pattern 1: Promise.all + run() — works with every provider

The simplest approach: fire off N run() calls in parallel, each on a distinct named branch. Each call spins up its own container — they're fully independent, no shared state:

import { run, opencode } from "@ai-hero/sandcastle";
import { docker } from "@ai-hero/sandcastle/sandboxes/docker";

const issues = ["42", "43", "44"];

const results = await Promise.all(
  issues.map(issue =>
    run({
      agent: opencode("opencode/big-pickle"),
      sandbox: docker(),
      branchStrategy: { type: "branch", branch: `agent/fix-${issue}` },
      promptFile: ".sandcastle/implement.md",
      promptArgs: { ISSUE_NUMBER: issue },
      maxIterations: 5,
    })
  )
);

// All three agents ran simultaneously — three containers, three branches
results.forEach(r => console.log(r.branch, r.commits.length));

No special provider required — this works with opencode(), claudeCode(), any provider. Each run() is a complete sandbox lifecycle.

Pattern 2: fork() — session-aware fan-out (Claude Code / Codex only)

A parent run explores the codebase, then forks independent child sessions from its context. Each child gets its own session JSONL and its own branch — but they share the parent's understanding of the code:

import { run, claudeCode } from "@ai-hero/sandcastle";
import { docker } from "@ai-hero/sandcastle/sandboxes/docker";

const parent = await run({
  agent: claudeCode("claude-opus-4-8"),
  sandbox: docker(),
  prompt: "Read the codebase and summarise the data model.",
});

const [reviewA, reviewB] = await Promise.all([
  parent.fork?.("Review the migration plan", {
    branchStrategy: { type: "branch", branch: "review-a" },
  }),
  parent.fork?.("Audit the auth layer", {
    branchStrategy: { type: "branch", branch: "review-b" },
  }),
]);

Fork is session-only — it isolates the agent's JSONL conversation, not the branch or sandbox. You must give each child its own named branch via branchStrategy. (ADR 0018)

fork() requires a resumable provider

fork() is present only on results from providers with sessionStorage: claudeCode(), codex(), and pi(). It is not available on opencode() or copilot(). If you need parallel runs with opencode(), use Pattern 1 above — it works with every provider.

createWorktree() — when worktrees need to outlive sandboxes

createWorktree() creates an independent worktree lifecycle separate from any sandbox. Use it when you want to run an interactive session first (human-in-the-loop), then hand the same worktree to a sandboxed AFK agent:

import { createWorktree } from "@ai-hero/sandcastle";

await using wt = await createWorktree({
  branchStrategy: { type: "branch", branch: "agent/fix-42" },
});

// Interactive session first — explore the code, plan the fix
await wt.interactive({
  agent: opencode("opencode/big-pickle"),
  prompt: "Explore the bug and plan a fix.",
});

// Then hand the same worktree to a sandboxed AFK agent
await wt.run({
  agent: opencode("opencode/big-pickle"),
  sandbox: docker(),
  prompt: "Implement the fix you planned.",
  maxIterations: 5,
});

The key difference: wt.interactive() defaults to noSandbox() — the agent runs on the host. Then wt.run() needs an explicit sandbox. The worktree persists between calls. (README)

APILifecycle ownerUse case
run()Automatic (sandbox created + destroyed)One-shot, no setup needed
createSandbox()You (sandbox stays alive between calls)Multiple agents on same branch, shared container state
createWorktree()You (worktree outlives sandbox)Interactive session → AFK handoff, or split ownership
Split ownership

When a sandbox is created via wt.createSandbox(), sandbox.close() tears down the container only — the worktree stays alive. wt.close() cleans up the worktree. This lets you create a sandbox, run an agent, tear down the container, then hand the same worktree to a new sandbox later.

The parallel-planner template

Sandcastle ships a ready-made template for exactly this pattern. Run:

npx @ai-hero/sandcastle init --template parallel-planner-with-review

It scaffolds a main.mts that: (1) asks a planner agent which issues can be parallelized, (2) runs implement + review on each in parallel, (3) merges all branches back. You don't have to build it from scratch — start from the template and customize. (README: templates)

Do it now

  1. Write a .sandcastle/implement.md prompt that uses {{ISSUE_NUMBER}} and !`git log --oneline -5`.
  2. In main.ts, wire up Promise.all with two run() calls, each on a different issue and a different named branch (e.g. agent/fix-1 and agent/fix-2).
  3. Run it. While it's running, open another terminal and run docker ps — you should see two containers alive simultaneously.
  4. After both complete, inspect: git branch --list 'agent/*' and git log --oneline agent/fix-1. Two branches, two independent commit histories.

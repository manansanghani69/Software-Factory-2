Lesson 0001

Your First Autonomous Run

Stand up a sandboxed agent that makes a real commit while you do nothing.

Why this matters

Your mission is a repo that runs without human intervention. Sandcastle's whole job is to let you fire off an agent, walk away, and come back to commits on a branch. This lesson gets that first loop running end-to-end on your machine.

The mental model

Sandcastle is an orchestrator, not an agent. You write a small TypeScript script; Sandcastle then:

  1. Creates a git worktree on a branch (per your branch strategy),
  2. Spins up a sandbox around it (a container via Docker/Podman, a microVM on Vercel, or nothing),
  3. Invokes a coding agent inside it with your prompt,
  4. Collects the commits it makes and merges them back per the branch strategy.

You don't talk to the model at all — you talk to run(). (README: How it works)

Two decisions drive everything else:

  1. Whose brain — the agent provider (claudeCode(), opencode(), codex(), pi()…).
  2. Where it lives — the sandbox provider (docker(), podman(), vercel(), noSandbox()).

See our reference: providers & branch strategies.

The unlock for you

opencode() is a first-class built-in agent provider — so you can run a fully autonomous agent without a Claude Code token. That removes the main setup blocker on your machine. (The trade-off: session-resume / structured-output retries currently need claudeCode, codex, or pi. (README: retries))

Stand it up

Pick a scratch repo — ideally a tiny one you own with a couple of issues or a README, so the agent has something to do. Then:

  1. Install the package. 
    npm install --save-dev @ai-hero/sandcastle
  2. Scaffold the sandcastle directory. 
    npx @ai-hero/sandcastle init

    Choose docker as the sandbox (Docker Desktop is your provider), opencode when it asks for the agent, and the blank template. It creates .sandcastle/ containing a Dockerfile, prompt.md, .env.example and .gitignore, then builds the container image. (README: CLI commands)

  3. Configure the token. Copy the env file and fill it in — for opencode you don't need an Anthropic key hitched to Sandcastle itself, but if you later switch to claudeCode() you'll want your token here: 
    cp .sandcastle/.env.example .sandcastle/.env
  4. Run your first agent. The scaffold generates main.ts (or main.mts) with a ready-made run(). Run it: 
    npx tsx .sandcastle/main.ts

    Watch it spin up the container, read your prompt, and start working. When it finishes, your repo has commits — made entirely by the agent.

Troubleshooting

If a run fails, Sandcastle writes logs under .sandcastle/logs/ (with logging: { type: "file" }, the default). Read the log file — that's where the actual error lives.

Anatomy of a run()

This is the one-shot call — sandbox lifecycle handled for you:

import { run, claudeCode } from "@ai-hero/sandcastle";
import { docker } from "@ai-hero/sandcastle/sandboxes/docker";

const result = await run({
  agent: claudeCode("claude-opus-4-8"), // whose brain (swap in opencode("opencode/big-pickle"))
  sandbox: docker(),                       // where it lives
  promptFile: ".sandcastle/prompt.md",   // what it works on
  maxIterations: 5,                        // how many passes before giving up
});

console.log(result.iterations.length); // how many iterations ran
console.log(result.commits);           // [{ sha }] — the work it made
console.log(result.branch);            // what landed where

Three things to notice for your mission:

  • It's AFK by design. run() is the autonomous path — no TTY required. (interactive() is the human-in-the-loop sibling.)
  • The prompt is a file you own. Sandcastle imposes no workflow opinion; your prompt.md is pure instructions. (README: prompts)
  • Default branch strategy for docker() is head — the agent writes straight into the host directory. Use branchStrategy: { type: "branch", branch: "agent/..." } to keep work off the main line. (That's the safe setting you'll use for real projects — lesson 0002.)

Check yourself

With branchStrategy: { type: "branch", branch: "foo" }, where do the agent's commits land?

For docker() bind-mount, how does agent output reach your disk?

What does an agent emitting <promise>COMPLETE</promise> cause?

Do it now

  1. Scaffold Sandcastle in a scratch repo (init → docker + opencode + blank).
  2. Edit .sandcastle/prompt.md to a real task — e.g. fix something small, and end it with a line telling the agent to print <promise>COMPLETE</promise> when done.
  3. Run npx tsx .sandcastle/main.ts and don't touch it.
  4. Afterwards, run git log --oneline and git status — inspect what the agent did.
  5. Check .sandcastle/logs/ to see how the run described itself.
Then what?

Next lesson we switch your scratch run to the safe workflow: branchStrategy: { type: "branch" } so agents never dirty the main line, and a second agent that reviews the first one's work. That's the nucleus of your autonomous pipeline.

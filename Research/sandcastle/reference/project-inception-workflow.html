From Idea to Implementation Tickets

A decision-first workflow for Wayfinder, documentation, and Sandcastle.

The governing rule

Wayfinder makes the route clear. Sandcastle travels the route. The workflow below exists to make scope, behavior, trade-offs, dependencies, and acceptance criteria explicit before an implementation ticket is created.

What this workflow is for

Use it for a greenfield project, a large feature, or a phase of an existing product. It accepts an input at any level of clarity—from a sentence of intent to a detailed PRD—and turns it into a bounded, reviewable set of implementation tickets.

The destination is not “a complete plan for the rest of time.” It is an execution-ready packet for the next phase, while later work remains visible as deliberate fog rather than false certainty.

Three approval boundaries

Human approval is explicit at the outcome gate, the phase-scope gate, and the execution-readiness gate. Agents can research, challenge, draft, and assemble evidence; they do not silently lock the product decision.

Two maps, one route

Wayfinder’s map and the execution scope map solve different problems. Keeping them distinct prevents a decision question from being mistaken for a build task.

Decision map

Wayfinder

Tracks the questions whose answers make the route clear. Its tickets are research, prototype, grilling, or prerequisite task work.

Completion: no unresolved decision remains on the route to the next phase.

Scope map

Project delivery tree

Tracks the approved decomposition from project to phase, outcome, capability, feature, story, and implementation task.

Completion: every next-phase leaf is an execution-ready ticket or an intentionally deferred decision.

The repository’s scope map is the canonical arbitrary-depth hierarchy. The issue tracker is a projection: it may use native parent-child relationships where available, but it must not be allowed to erase intermediate levels.

Rolling phases

Planning does not stop the moment phase one begins. It moves like a wave: implementation proceeds on a locked slice while the next slice becomes clearer.

Phase N — locked

Documents approved, tickets ready, Sandcastle can execute.

Phase N+1 — shaping

Research and decision tickets are active; rough scope may be drafted.

Later — fog

Known direction, not yet a precise question. Do not pre-slice it into fake tickets.

Do not over-plan

Future phases can have intent, boundaries, and visible unknowns. They should not have implementation tickets that depend on decisions nobody has made yet.

What makes a document trustworthy?

Every document has an ID, type, status, owner, phase, parent, dependencies, supersession links, and last-updated date. Its body states the decision or contract, not just a stream of discussion. If a document is intentionally skipped, the document index says why.

Arbitrary-depth ticket hierarchy

The hierarchy is a tree for decomposition and a graph for dependencies. A ticket can have one structural parent while being blocked by several other tickets.

  • Project: Shared workspace
    • Phase 1: Invite members
      • Outcome: Owners can add collaborators
        • Capability: Membership management
          • Feature: Email invitation
            • Story: Invitee receives a usable invitation
            • Task: Add invitation endpoint
            • Task: Add invitation acceptance flow
            • Task: Add expiry and replay tests

Decision tickets sit beside this tree and unblock it. For example, “What happens when an invitation is resent?” is a grilling ticket. Once answered, the feature spec and acceptance model can be updated; only then do the leaf tasks become ready.

Ticket contract

An implementation ticket is a compact execution packet, not a pointer to an unexplained conversation.

id: EXEC-INVITE-01
type: execution
status: ready
parent: feature/email-invitation
depends_on: [DEC-INVITE-EXPIRY]
source_docs: [feature/email-invitation/spec.md, feature/email-invitation/api.md]

## Objective
Allow an owner to send an invitation to a collaborator.

## Scope
- Add the invitation operation and its validation.
- Do not change role editing or bulk invitations.

## Behavior
- A valid owner can invite an email address.
- A duplicate active invitation is handled according to the approved spec.
- Expired invitations cannot be accepted.

## Acceptance
- [ ] Valid invitation is created and observable.
- [ ] Unauthorized caller is rejected.
- [ ] Expired invitation cannot be accepted.
- [ ] Automated tests cover the listed cases.

## Validation
Run the project test command and the focused invitation test suite.

Traceability

Every implementation decision should be explainable by walking backward from the ticket to the outcome.

Outcome→Scope node→Document→Acceptance→Execution ticket→Sandcastle run

The reverse path matters too: if an approved document changes, the workflow can find affected tickets, mark them stale, and reopen only the impacted subtree.

Failure and change recovery

  1. Stop the affected subtree. Do not restart unrelated work or silently continue with stale assumptions.
  2. Record the new uncertainty. Create a precise Wayfinder decision ticket, or place it in the fog if it is not yet precise enough.
  3. Resolve and update evidence. Change the glossary, spec, design, contract, or ADR that carries the decision.
  4. Recompute impact. Mark affected documents and tickets stale, then recalculate dependencies and waves.
  5. Re-run the readiness gate. Create or reissue execution tickets only for the corrected subtree.
The stopping condition

Planning for a phase is complete when every in-scope implementation ticket is ready, dependencies are ordered, required documents exist, and remaining uncertainty is either assigned to a later phase or explicitly out of scope.

      What work serves the outcome?

      Project └─ Delivery Slice [outcome attached] └─ Capability └─ Feature └─ Story └─ Task └─ Subtask

      Skip unhelpful levels. A Story can be executable; a Story grouping Tasks can be a container. Set that role explicitly.

      Native GitHub limits: eight nested sub-issue levels and 100 children per parent. Deeper conceptual branches use visible linked continuation roots.

      Outcome→Scope node→Rule / contract→Acceptance example→Execution issue

      Follow the links backward to explain an issue; follow them forward to find affected work when a decision changes. Repository documents own definitions. GitHub owns live work state and native relationships.

      When approved behavior changes

      Record trigger → resolve the question → mark affected definitions/issues stale → update evidence → recompute coverage and dependencies → repeat relevant gates → resume authorized work.

      A future slice can propose a new contract. Changing the baseline of running work requires impact review and controlled reopening. Marking an issue stale must be accompanied by stopping/blocking its actual implementation consumer.

      What reaches implementation?

      A bounded issue set plus accessible definitions and verification guidance.

      Packet itemWhat the implementer can understand
      Outcome and scopeWhy this slice exists, what is included, and where it stops.
      Approved definitionsRules, examples, designs, contracts, data, and relevant constraints at named revisions.
      Issue hierarchyWhat each unit contributes; container versus executable role; parent and source links.
      DependenciesReal blockers, shared-resource coordination, and available execution frontier.
      Acceptance and proofObservable completion, checks, and slice integration acceptance.
      Discretion and recoveryWhat can be decided locally, and which material discoveries reopen approval.
      How partial GitHub publication resumes

      Each approved unit has a stable work ID. The publisher reads existing issues, records each resulting URL immediately, and wires relationships in a second pass. On interruption it reconciles that ledger against GitHub, then reads back the entire approved set. This prevents a retry from blindly duplicating issues.

      Which decisions belong to the human?

      Outcome choice, appetite, evidence acceptance, business/legal judgment, residual risk acceptance, and all four baselines. AI researches facts, interviews, challenges omissions, drafts and cross-checks. Unsupported AI conclusions remain assumptions.

      How small changes can use a lighter path

      Reuse applicable approved intent and definitions. Assess the change dimensions, specify focused behavior/examples, draft the issue, and combine Definition/Readiness review when appropriate. New material uncertainty returns to the broader route.
